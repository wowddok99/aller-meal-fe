# UI/UX 의사결정 워크플로

이 문서는 AllerMeal 프론트엔드에서 사용자에게 보이는 UI를 제안하거나 수정할 때 적용한다. 목표는 화면 단위의 즉흥적인 배치와 반복 수정 대신, 제품 구조와 사용 목적에 근거한 일관된 결정을 내리는 것이다.

## 1. 작업을 먼저 분류한다

다음은 미세 UI 수정이 아니라 **구조 설계 작업**이다.

- 헤더, 메뉴, 탭, 사이드바, 카테고리, 화면 그룹, 라우트 진입 구조 변경
- 카드, 목록, 표 등 정보를 표현하는 구조 또는 정보 위계 변경
- 공통 컴포넌트 또는 여러 화면의 읽기 순서와 반응형 배치에 영향을 주는 변경
- 사용자가 “어색하다”, “개선안”, “추천”, “어떻게 해야 하냐”고 요청했고, 수정할 구조나 의도가 명확히 지정되지 않은 경우

단순 문구 교체, 명확한 단일 값 수정, 사용자가 정확히 지정한 국소 스타일 수정은 미세 UI 수정으로 처리하고 바로 구현할 수 있다. 범위가 모호하거나 공통·다중 화면에 영향을 주면 구조 설계 작업으로 분류한다.

## 2. 구조 설계 작업의 근거를 확인한다

제안이나 구현 전에 아래를 확인한다.

1. 관련 화면 전체와 실제 라우트
2. 공통 Shell, Header, Navigation의 현재 구현
3. 각 화면이 전역 탐색 목적지인지, 영역 내부 목적지인지, 특정 객체의 하위 흐름인지, 가입·인증 같은 상태 화면인지
4. 데스크톱과 모바일에서 사용자가 같은 목적지에 도달하는 방식
5. 현재 구조가 만드는 탐색, 밀도, 정렬, 클릭 영역, 읽기 순서의 문제와 영향 범위

Page Index, 작업 목록, API 목록, 파일 목록의 항목을 실제 사용자 메뉴 구조로 그대로 사용하지 않는다. 메뉴는 화면 이름이 아니라 사용자의 목적과 업무 흐름을 기준으로 설계한다.

## 3. 제안은 결정 가능한 형태로 제시한다

구조 설계 제안에는 반드시 아래 내용을 포함한다.

- 현재 문제와 그 문제가 사용자에게 만드는 결과
- 변경 범위: 전역 UI, 특정 업무 영역, 개별 화면 중 어디까지인지
- 화면 분류: 전역 메뉴, 영역 내부 메뉴, 흐름 진입점, 상태 화면
- 결정에 실제 선택지가 남아 있을 때만, 실현 가능한 대안과 각각의 트레이드오프
- 권고안 한 가지와 선택 이유
- 메뉴 트리 또는 텍스트 와이어프레임
- 데스크톱과 모바일에서의 탐색·접힘·활성 상태
- 수정할 공통 컴포넌트와 영향을 받는 화면

일반적인 관례, 익숙한 템플릿, 단일 스크린샷만으로 결론을 내리지 않는다. 기존 코드와 관련 화면에서 확인한 근거를 먼저 제시한다.

## 4. 구조 설계는 확정 뒤에 구현한다

사용자가 “제안”, “추천”, “방법”, “어떻게 할지”를 요청한 경우 코드를 수정하지 않는다. 헤더, 내비게이션, 정보 구조처럼 여러 화면에 영향을 주는 변경은 권고안을 제시하고 사용자가 방향을 확정한 뒤에 구현한다. 사용자가 구조와 의도를 명확히 지정해 구현을 요청하면, 별도 재확인 없이 그 범위에서 구현한다.

확정 전에는 임의 CSS 조정, 컴포넌트 재배치, 시안 구현으로 방향을 시험하지 않는다. 사용자가 구현을 요청한 뒤에도 합의된 구조를 벗어나는 선택이 필요하면 근거와 영향을 먼저 설명한다.

## 5. 시각 피드백은 원인을 진단한 뒤 한 번에 수정한다

사용자가 정렬, 간격, 밀도, 비율, 클릭 상태가 어색하다고 말하면 값을 바로 조정하지 않는다. 먼저 기준선, 컨테이너 폭, 그리드, 읽기 순서, 클릭 영역, 반응형 규칙 가운데 원인을 식별하고 설명한다.

하나의 피드백에 대한 수정은 하나의 일관된 가설과 변경안으로 묶는다. 같은 문제를 해결한다는 이유로 서로 다른 방향의 CSS 시도를 연속으로 적용하지 않는다.

## 6. 구현 후 화면 전체를 검증한다

UI 구현 또는 수정 후에는 다음을 확인한다.

- 실제 브라우저에서 대상 route를 480px 모바일과 1280px 데스크톱으로 확인한다.
- 테마를 지원하면 라이트와 다크 모드를 모두 확인한다.
- 변경한 링크와 버튼의 기본, hover, active, keyboard focus 상태를 확인한다.
- 제목, 설명, 수치, 링크, 카드 여백, 정렬, 줄바꿈을 같은 화면에서 함께 검토한다.
- 공통 UI 변경이면 영향받는 대표 화면을 함께 확인한다.

검증 화면에서 정렬, 여백, 줄바꿈, 상호작용 상태가 어색하면 완료로 보고하지 않는다.
